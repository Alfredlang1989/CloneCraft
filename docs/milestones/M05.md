# M05 contract - RocksDB persistence

## Purpose

Add durable backend-neutral persistence for the authoritative logical world
after the hot-projection boundary is established.

RocksDB is one backend behind the persistence interface. Gameplay code does not
speak RocksDB directly.

## Build dependency

RocksDB is supplied by the host and must pass
`tools/check_host_dependencies.py --current` before M05 planning begins. Use
the `OmniGrid::RocksDB` CMake target prepared by
`cmake/OmnigridThirdParty.cmake`. Do not vendor, download, build or install a
second RocksDB copy inside the repository. The M05 backend configuration calls
`omnigrid_require_rocksdb()` and links `OmniGrid::RocksDB`; it must not grow a
second ad-hoc `find_library` path.

## Data model

Persist at minimum:

- authoritative base-world deltas / block mutations that must survive restart;
- registered sparse Sidecars across their canonical scopes;
- stable logical entity/object state introduced before/with M04 where declared
  persistent;
- schema/version metadata needed to decode stored records safely.

Do not persist process-local handles such as raw runtime pointers,
`entt::entity`, Jolt/Ogre handles, or raw transient numeric content IDs without
stable name/schema mapping.

Keys are deterministic and based on stable world/object identity. Hierarchical
world addresses remain hierarchical; persistence must not reintroduce a global
floating or overflow-prone flattened coordinate identity.

## Interface and backend

Define a backend-neutral persistence interface with clear read/write/batch and
lifecycle semantics. RocksDB implementation sits behind it.

Serialization is versioned and deterministic. Unknown/incompatible schema
versions fail explicitly rather than being silently interpreted.

A logical multi-record mutation that must be atomic uses crash-consistent batch
semantics (`WriteBatch` or equivalent backend abstraction).

## Dirty tracking

Dirty state is generated by the authoritative mutation/change funnel, not by
polling the renderer/ECS. No-op writes do not create false dirty work.

Dirty tracking must distinguish what can be batched/coalesced without losing
required state transitions. Persistence clearing occurs only after successful
write acknowledgment.

## I/O ownership

Persistence I/O may use a worker/queue. The I/O worker does not directly mutate
WorldState, Lua, ECS or renderer state. Completed reads/writes return through
owned handoff structures to the owner/game thread.

Queue capacity/backpressure and shutdown/flush semantics are explicit. Engine
shutdown must not silently lose accepted dirty state.

## Recovery

Startup loads durable state into the normal authoritative representation without
creating a second gameplay mutation API. Corrupt/incompatible records produce
clear failures/quarantine policy rather than undefined state.

Base generated world remains reproducible; persistence stores the durable
changes/state required on top of it rather than blindly serializing every
materialized voxel unless a later data-driven policy explicitly chooses that.

Timer persistence is deliberately outside the default M05 scope unless a
separate durable clock/deadline model is specified. Never store raw
`steady_clock::time_point`.

## Mandatory proofs

1. block delta survives process restart/load cycle;
2. sparse Sidecars at representative Block + higher hierarchy scopes survive
   restart with exact values/default-removal semantics;
3. persistent logical entity/object state survives demotion/restart/promotion;
4. stable keys do not contain raw process-local handles/runtime-only IDs;
5. WriteBatch/crash-consistent logical mutation test proves no partial accepted
   state for a defined batch;
6. dirty state clears only after successful backend acknowledgment and remains
   dirty on injected write failure;
7. bounded I/O queue/backpressure and clean shutdown/flush behavior are tested;
8. schema version mismatch/corrupt record fails deterministically;
9. persistence worker never mutates WorldState/ECS/Lua directly;
10. reload does not bypass the architecture with a parallel mutable world store;
11. architecture rules classify persistence module/dependency direction;
12. M01-M04 regressions remain green and reviewer `./compile.sh` passes.
