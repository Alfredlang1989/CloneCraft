# M04 contract - enTT hot-state projection

## Purpose

Introduce enTT for active/hot dynamic state without changing the authoritative
world-state or communication semantics established by M01-M03.

M04 is projection architecture, not an ECS rewrite of the voxel world.

## Build dependency

Use the pinned EnTT v3.16.0 distribution already present under
`third_party/entt/` through the `EnTT::EnTT` CMake target. M04 must not replace
the pin with a host package, network fetch or second vendored copy.

## Ownership model

- WorldState remains authoritative for persistent/logical voxel and Sidecar
  state.
- enTT owns only active/hot runtime projection state that benefits from ECS
  iteration.
- raw `entt::entity` is process-local and never a persistent/public/network
  identity.
- a stable logical entity/object identity maps to the current `entt::entity`
  while promoted.
- normal static voxel blocks do not get one ECS entity each.

## Lifecycle

Establish explicit states and transitions rather than implicit magic:

`cold logical state -> warm/materialized state -> hot ECS projection`

and

`hot ECS projection -> warm/logical state -> cold/evictable state`

Promotion must:

1. identify the stable logical object;
2. create/map its transient ECS entity;
3. hydrate registered active components from authoritative logical state;
4. publish activation only after required state is coherent.

Demotion must:

1. reconcile persistent component state back through the approved logical state
   boundary;
2. remove transient mapping/components;
3. leave stable identity and persistent data intact.

Promotion/demotion must be lossless for all properties declared persistent.
Transient-only components may be discarded only by explicit schema/contract.

## Component architecture

M04 must establish a generic registry/descriptor boundary so engine code does
not hard-code game component names. The design must leave room for future
game/Lua-declared component schemas even if M04 initially implements a bounded
set of engine-side component storage types.

Do not encode game semantics into the ECS bridge merely because the first proof
uses a particular entity/component.

## Threading

The enTT registry and promotion/demotion mutation are owner/game-thread state
unless a later architecture change explicitly introduces partitioned ownership.
Workers may prepare immutable data but do not mutate the live registry.

## Communication

Public gameplay mutation and actions continue through the existing
CommunicationEnvelope/runtime. ECS systems that need authoritative world
changes emit/use the same contract. Do not add an ECS event universe beside the
bus.

Messages never expose raw `entt::entity` as durable identity.

## Architecture/tooling work

If a new ECS module/source tree is added, update
`tools/architecture_rules.json` so dependency direction is executable. The
preferred direction is projection -> authoritative state/registry/core, never
WorldState -> enTT implementation.

## Mandatory proofs

1. Stable logical ID maps to one current hot `entt::entity` and back.
2. cold -> warm -> hot promotion hydrates expected registered state.
3. hot -> warm demotion preserves all persistent logical state.
4. promote -> mutate through approved path -> demote -> promote reproduces the
   same persistent values.
5. destroyed/removed logical object cannot leave a live stale ECS mapping.
6. repeated promotion/demotion does not duplicate entities or leak mappings.
7. a normal chunk with many voxels does not allocate an ECS entity per voxel.
8. no persistent/network serialization contains raw `entt::entity`.
9. M01-M03 public WorldState and Communication APIs remain compatible.
10. owner-thread violations are rejected/tested where practical.
11. architecture checker classifies the new module and prevents reverse
    dependency from authoritative state into the ECS implementation.
12. reviewer `./compile.sh` passes.
